The proof, from the compiler

A policy page can promise anything. This page shows what the cancho compiler proves about the gateway binary’s capability boundary — a report it derives, a report committed in the repository, a report CI holds against a ceiling a person reviews. The upstream policy inside that boundary is enforced by the gateway and tested, not proved; the four jobs are separated below. Every table below is spliced from that report by scripts/proof.py; if you edit this page by hand, CI fails.

What an authority report is

The compiler does not only build the binary; it writes down what that binary can do. Not what it promises. Not what its documentation says. What its instructions can reach.

A capability can be released before the program starts — cancho’s model is that the binary simply does not have it. The gateway’s report is bounded: the compiler says so, and CI re-derives it on every push and fails if a change widens it past the ceiling in authority.toml. To give the gateway a new capability is to write a diff a person must review.

Derived, not declared

The report is what the compiler derives from the source. The committed file must equal it, byte for byte, or CI fails.

Ceiling-checked

authority.toml is what a person reviews: a ceiling the derived set may be smaller than, never larger.

Held in CI

scripts/authority.py --check re-derives the report on every push. Widening the gateway is a reviewable change, not an accident.

Four different jobs, four different kinds of trust — read them as the claim, because the word “proof” on this page covers the first and not the rest:

The compiler proves the capability boundary

What the binary can reach: files, foreign code, memory, one network bound. Derived, bounded, recorded.

The gateway enforces the upstream policy

Which hosts it will connect to: compiled in from the deployment file, exact match before every connect. Code, not proof — never presented as proof here.

Tests challenge the enforcement

The upstream set is exercised by the suite, not trusted because it was written down.

CI keeps the evidence aligned with the source

Report, ceiling and corpus re-derived on every push; a drifting page or manifest is a red build, not a stale claim.

Break it yourself

The demo binary from the latest release listens on 8080 and forwards to one upstream on 127.0.0.1:9000. Everything below is one of the gateway’s own tests (tests/proxy_test.py), and every refusal carries a rule tag and a request id.

# an upstream for the demo binary to forward to (terminal 1)
python3 -m http.server 9000

# the demo gateway (terminal 2), or build your own deployment:
./cancho-gateway-demo-linux-x86_64
{"t":102,"id":"1a-1f90-00000014","method":"GET","path":"/", ... "status":200}

# now try to smuggle a request past it (terminal 3):
curl -i http://127.0.0.1:8080/x -H 'Content-Length: 5' -H 'Transfer-Encoding: chunked'
HTTP/1.1 400 ... "rule":"framing.two-lengths"
printf 'GET / HTTP/1.1\nHost: a\n\n' | nc 127.0.0.1 8080
HTTP/1.1 400 ... "rule":"framing.line-ending"
curl -i http://127.0.0.1:8080/ -H 'Host: a' -X CONNECT
HTTP/1.1 501 ... "rule":"framing.method-unsupported"
curl -i http://127.0.0.1:8080/ -H 'Host: a' --data-binary @2MB
HTTP/1.1 413 ... "rule":"limit.body"

Every one of these closes the connection. The framing rules are deliberately stricter than the RFC where tolerance is a smuggling lever: chunk extensions refused, trailer fields refused, no whitespace around a chunk size. The evidence page has the corpus (67 head cases, 43 chunked-body cases, llhttp’s among them) and what running it found.

The demo binary’s own report ships with the release: cancho-gateway-demo.authority.json, built in CI from the same committed sources (download).

Or send your bytes from the browser: the refusal lab — the same framing judge, verified against the probe’s recorded answers on every load.

What this proof does not say

A proof that hides its edges is marketing. These are the edges.

  • The upstream set is not compiler-proved — it is enforced by the gateway, not proved by the compiler. A cancho program has one network bound shared by listening and connecting, so the report says net_out(""): not narrowed. The upstream set is compiled in from the deployment file and enforced by exact match before every connect, and tested — but the compiler does not vouch for it. The design says so in section 2.
  • It is not a security review. The report bounds the binary’s capabilities; it does not certify that the logic inside those bounds is free of bugs. The tests and the corpus are the other half of the story, and they are not a substitute for an external audit. Alpha: not for production.
  • The admin port has no authentication. It binds every interface; firewall it. Inside the bounds, a bad decision is still a decision.
  • The TLS engine is not independently reviewed. TLS 1.3, ECDSA P-256, written in cancho (docs/tls.md), reading exactly two paths — and no one outside has looked at it yet.

Why this exists

cancho is a typed systems language where the compiler writes down what a program may do. For code you did not write yourself — a proxy, a dependency, an agent’s output — “the report says what it can reach” is the only sentence that scales with distrust.

The language: cancho. The gateway’s sources: this repository. The manifesto: alpibru.com/manifesto.
