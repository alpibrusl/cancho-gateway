Where it earns its place.

Eight situations. Each has the deployment file, the commands to run it in a terminal, and what you should see. Every command and every line of output below was run against the real gateway.

Download and try it

The configuration is compiled into the binary, so a release carries a demo gateway: it listens on port 8080 and forwards to one upstream on 127.0.0.1:9000. To point a gateway at your own upstreams you build your own, from the sources in the same release (examples 1 to 6 do exactly that).

Download the binary (Linux x86-64) All assets and checksums

1Download, check and start it (terminal 1), with any upstream on port 9000 (terminal 2):

# terminal 2
python3 -m http.server 9000

# terminal 1
chmod +x cancho-gateway-demo-linux-x86_64
./cancho-gateway-demo-linux-x86_64                 # one JSON line per request appears here

2In terminal 3, a normal request, then the smuggling shape:

curl -si localhost:8080/ | head -8
curl -si localhost:8080/ -H 'Content-Length: 1' -H 'Transfer-Encoding: chunked' -d x
HTTP/1.0 200 OK
...
Via: 1.1 cancho-gateway
X-Request-Id: 594fe-1f90-00000001

HTTP/1.1 400 Bad Request
...
{"type":"about:blank","title":"Bad Request","status":400,"rule":"framing.two-lengths","request_id":"594fe-1f90-00000002"}

Each release has the binary, cancho-gateway-demo.authority.json (what the compiler says the binary may do), cancho-gateway-src.tar.gz and SHA256SUMS; check with sha256sum -c SHA256SUMS. Built in CI at the pinned compiler by scripts/release.sh. It links only libc. If no release is listed yet, the first one has not been published: build from source below. Alpha: not for production.

Build from source, once

Examples 1 to 8 build a gateway for each deployment file. That needs the pinned cancho compiler and Python 3. Nothing is installed system-wide, and scripts/try.sh builds in a temporary copy, so your checkout stays clean.

git clone https://github.com/alpibrusl/cancho && git clone https://github.com/alpibrusl/cancho-gateway
git -C cancho checkout "$(sed -n 's/^cancho *= *"\([0-9a-f]*\)".*/\1/p' cancho-gateway/cancho.toml)"
(cd cancho && cargo build --release -p cancho)
export PATH="$PWD/cancho/target/release:$PATH"
cd cancho-gateway

Every example uses three terminals in cancho-gateway/: 1 an upstream (scripts/demo_upstream.py, which answers every request with the request it received, so you see exactly what the gateway forwarded), 2 the gateway (scripts/try.sh <deployment>, Ctrl-C stops it) and 3 curl. Request ids and times differ on your machine.

1. Internal APIs behind a TLS front

Caddy or nginx terminates TLS and sets X-Forwarded-For. The gateway sits behind it. For the host that front serves it believes the forwarding headers; for any other host it does not. Every request gets an id the services and the audit log share.

Deployment: deploy/examples/front.toml

# Example 1: behind a TLS-terminating front that sets the forwarding headers.
listen = 8080

[[upstream]]
name = "orders"
addr = "127.0.0.1:9000"

[[route]]
name = "orders"
host = "api.example.com"
path_prefix = "/"
upstream = "orders"
trust_forwarded = true     # the party in front is mine: pass its forwarding headers on

[[route]]
name = "public"
path_prefix = "/"
upstream = "orders"        # any other host: forwarding claims are not believed

1In terminal 1, start the upstream. It answers every request with the request it received.

python3 scripts/demo_upstream.py 9000 9001
listening on 127.0.0.1:9000, 127.0.0.1:9001

2In terminal 2, build this deployment and run it (from the repository root).

scripts/try.sh deploy/examples/front.toml
gateway built from deploy/examples/front.toml; listening, one JSON line per request below (Ctrl-C stops it)

3In terminal 3, send a request as the trusted front would, claiming a client address and an id:

curl -si localhost:8080/orders/7 -H 'Host: api.example.com' \
  -H 'X-Forwarded-For: 203.0.113.9' -H 'X-Request-Id: abc-123'
HTTP/1.1 200 OK
Via: 1.1 cancho-gateway
X-Request-Id: abc-123
...
upstream :9000 saw
GET /orders/7
Host: api.example.com
X-Forwarded-For: 203.0.113.9      <- passed on: this route trusts its front
X-Request-Id: abc-123
Via: 1.1 cancho-gateway

4Now the same claims from a host this gateway does not trust:

curl -si localhost:8080/orders/7 -H 'Host: other.example.com' \
  -H 'X-Forwarded-For: 203.0.113.9' -H 'X-Request-Id: abc-123'
X-Request-Id: 81fb4-1f90-00000003      <- the claimed id was replaced
...
upstream :9000 saw
GET /orders/7
Host: other.example.com
Via: 1.1 cancho-gateway               <- no X-Forwarded-For: it was removed
X-Forwarded-Host: other.example.com
X-Forwarded-Proto: http
X-Request-Id: 81fb4-1f90-00000003

5Terminal 2 has one JSON line for each request, with the route that took it:

# terminal 2, as it happens
{"id":"abc-123","method":"GET","path":"/orders/7","route":"orders","upstream":"orders","status":200,"rule":"","outcome":"ok","ms":42,...}
{"id":"81fb4-1f90-00000003","method":"GET","path":"/orders/7","route":"public","upstream":"orders","status":200,...}

A client’s X-Request-Id is kept only on a trusted route, and only if it is 1 to 64 characters of letters, digits, ., _ and -. The full table.

2. One door for a few services

Route by host, then by the longest path prefix, and by method. Static files are read-only; a method no route allows is refused at the door, not discovered at the service.

Deployment: deploy/examples/door.toml

# Examples 2, 4 and 6: one door for two services; static files are read-only.
listen = 8080

[[upstream]]
name = "web"
addr = "127.0.0.1:9000"

[[upstream]]
name = "api"
addr = "127.0.0.1:9001"

[[route]]
name = "web-static"
path_prefix = "/static"
methods = ["GET", "HEAD"]
upstream = "web"
max_body = 0

[[route]]
name = "api"
path_prefix = "/api"
upstream = "api"

[[route]]
name = "web"
path_prefix = "/"
methods = ["GET", "HEAD"]   # a method no matching route allows is refused 405; one that another, shorter route allows falls through to it
upstream = "web"

1Terminal 1: python3 scripts/demo_upstream.py 9000 9001 (two upstreams, ports 9000 for the web and 9001 for the API). Terminal 2: scripts/try.sh deploy/examples/door.toml.

# terminal 3: where each request goes
curl -s localhost:8080/index.html | head -2
curl -s localhost:8080/api/orders | head -2
upstream :9000 saw
GET /index.html
upstream :9001 saw
GET /api/orders

2A method the matching routes do not allow:

curl -si -X POST localhost:8080/static/app.js
HTTP/1.1 405 Method Not Allowed
Content-Type: application/problem+json
X-Request-Id: 9af94-1f90-00000002
...
{"type":"about:blank","title":"Method Not Allowed","status":405,"rule":"route.method","request_id":"9af94-1f90-00000002"}

3The same method on a route that allows it:

curl -si -X POST localhost:8080/api/x -d hi | head -1
curl -s -X POST localhost:8080/api/x -d hi | grep -E 'saw|body'
HTTP/1.1 200 OK
upstream :9001 saw
body bytes: 2

If a shorter route does allow the method, the request falls through to it instead of being refused: the longest prefix that allows the method wins. Ties between two routes are a configuration error, found when the deployment is generated.

3. Upload limits that are enforced

A route sets the largest body it accepts. The declared length is checked before a byte is forwarded; a chunked body is counted as it arrives.

Deployment: deploy/examples/uploads.toml

# Example 3: a route sets the largest body it accepts.
listen = 8080

[[upstream]]
name = "reports"
addr = "127.0.0.1:9000"

[[route]]
name = "reports"
path_prefix = "/reports"
methods = ["POST"]
upstream = "reports"
max_body = 1024            # 1 KiB here, so the example is quick; 5242880 would be 5 MiB

1Terminal 1: python3 scripts/demo_upstream.py 9000 9001. Terminal 2: scripts/try.sh deploy/examples/uploads.toml. Terminal 3, a body inside the limit (1 KiB here):

head -c 100 /dev/zero | curl -si localhost:8080/reports -X POST --data-binary @- | grep -E '^HTTP|body'
HTTP/1.1 200 OK
body bytes: 100

2A body over it:

head -c 5000 /dev/zero | curl -si localhost:8080/reports -X POST --data-binary @-
HTTP/1.1 413 Content Too Large
Content-Type: application/problem+json
...
{"type":"about:blank","title":"Content Too Large","status":413,"rule":"limit.body","request_id":"9bcf6-1f90-00000003"}

3Terminal 2 shows the refusal as data, and that nothing was forwarded (upstream_ms and bytes_in are 0):

# terminal 2
{"id":"9bcf6-1f90-00000003","method":"POST","path":"/reports","route":"reports","upstream":"reports","status":413,"rule":"limit.body","outcome":"refused","ms":0,"upstream_ms":0,"bytes_in":0,"bytes_out":267}

The default limit is 1 MiB. A chunked body over the limit is cut off after part of it may already have gone upstream; the proxy notes say so.

4. A strict door in front of a lenient server

Old application servers and hand-written backends often disagree with a front proxy about where a request ends. That disagreement is request smuggling. The gateway refuses the ambiguous shapes, closes the connection, and the backend never sees them. Use any deployment above; this one needs the upstream running to prove nothing reaches it.

With the gateway of example 2 (or the downloaded demo binary) running, in terminal 3:

1Two body lengths, the classic smuggling shape:

printf 'POST / HTTP/1.1\r\nHost: a\r\nContent-Length: 5\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\n' | nc -q1 localhost 8080
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
...
{"type":"about:blank","title":"Bad Request","status":400,"rule":"framing.two-lengths","request_id":"848cc-1f90-00000006"}

2Two different lengths:

printf 'GET / HTTP/1.1\r\nHost: a\r\nContent-Length: 5\r\nContent-Length: 6\r\n\r\n' | nc -q1 localhost 8080 | tail -1
{"type":"about:blank","title":"Bad Request","status":400,"rule":"framing.length","request_id":"848cc-1f90-00000007"}

3A CONNECT tunnel:

printf 'CONNECT example.com:443 HTTP/1.1\r\nHost: example.com:443\r\n\r\n' | nc -q1 localhost 8080 | tail -1
{"type":"about:blank","title":"Not Implemented","status":501,"rule":"framing.method-unsupported","request_id":"848cc-1f90-00000008"}

Others refused with their own rule: obsolete header line folding (framing.fold), a bare LF line ending (framing.line-ending), an absolute-form target (framing.target-form). Tested against a corpus, split at every byte and mutated; the evidence page lists what that found. nc is netcat; any tool that sends raw bytes does.

5. A flaky upstream that should not take everything down

After a run of failures the gateway stops sending requests to that upstream for a while, answers at once, and lets one trial request through to see whether it is back. Here the upstream is simply not running.

Deployment: deploy/examples/flaky.toml

# Example 5: an upstream that is down. Do not start it, then watch the circuit open.
listen = 8080
circuit_threshold = 3       # consecutive failures that open the circuit
circuit_open_ms = 5000      # how long it stays open
connect_timeout_ms = 1000

[[upstream]]
name = "orders"
addr = "127.0.0.1:9000"

[[route]]
name = "orders"
path_prefix = "/"
upstream = "orders"

1Do not start an upstream. Terminal 2: scripts/try.sh deploy/examples/flaky.toml. Terminal 3, five requests:

for i in 1 2 3 4 5; do curl -s -o /dev/null -w '%{http_code} ' localhost:8080/x; done; echo
502 502 502 503 503

2The first three fail to connect (502, proxy.connect); the circuit opens; the rest are refused at once (503):

curl -si localhost:8080/x
HTTP/1.1 503 Service Unavailable
...
{"type":"about:blank","title":"Service Unavailable","status":503,"rule":"proxy.circuit-open","request_id":"9cc2c-1f90-00000006"}

3Start the upstream in terminal 1 (python3 scripts/demo_upstream.py 9000) and wait more than 5 seconds. The next request is the trial; if it succeeds the circuit closes:

sleep 6; curl -si localhost:8080/x | head -1
HTTP/1.1 200 OK

Other upstream failures keep their own tags: proxy.upstream-closed and proxy.head (502) and timeout.*. A dead idle connection is retried once, and only for a request with no body that is safe to repeat.

6. An audit trail, health and metrics

When someone asks “what happened to request X”, “is it healthy” or “what can this process touch”, there is an answer for each. Health and metrics are on a second port, admin_listen in the deployment (example 2’s file has it, on 9090).

1Keep the access log: redirect the gateway’s output to a file (or to journald), send some requests, then ask it questions:

scripts/try.sh deploy/examples/door.toml > access.log     # terminal 2; terminal 1 runs the upstream, as in example 2

# terminal 3
curl -s localhost:8080/index.html >/dev/null; curl -s -X POST localhost:8080/static/a >/dev/null
grep '"status":4' access.log                        # what was refused
grep '<an id from a response>' access.log           # one request, by the id the client was given
{"t":1791402183873,"id":"848cc-1f90-00000002","method":"POST","path":"/static/a","route":"","upstream":"","status":405,"rule":"route.method","outcome":"refused","ms":0,...}

2Is it alive, and is it ready to take traffic? /readyz says why not, as data:

curl -si localhost:9090/healthz
curl -si localhost:9090/readyz
HTTP/1.1 200 OK
Content-Type: application/json
...
{"alive":true}

HTTP/1.1 200 OK
...
{"ready":true}

# with an upstream's circuit open (example 5):
HTTP/1.1 503 Service Unavailable
{"ready":false,"why":["upstream orders: circuit open"]}

3Counters by route, status class and rule, and latency histograms, as JSON or as Prometheus text:

curl -s localhost:9090/metrics | python3 -m json.tool | head -30
curl -s 'localhost:9090/metrics?format=prometheus' | grep -E 'requests_total|refusals_total'
cancho_gateway_requests_total{route="web",class="2xx"} 1
cancho_gateway_requests_total{route="web",class="4xx"} 0
cancho_gateway_refusals_total{rule="route.method"} 1

4Ask the compiler what the program may do (the gateway’s report is committed and CI checks it):

python3 scripts/authority.py --check        # derives it with the compiler, fails if it differs from the recorded one
cat manifests/gateway.authority.json              # the recorded report
gateway  args, clock, conn_accept, conn_read, conn_write, heap,
         io_write, net_in(""), net_out(""), poll        # no foreign calls, no writes; reads files only for TLS (example 7)

The id is also in the response header and in a refusal’s body. The log goes to stdout, so journald, a file or a collector can take it; if that reader stops, so does the gateway (see the alpha notes). The admin port listens on every interface (the compiler offers no loopback-only bind): it shows route and upstream names and counters, no request data, but firewall it. The network bound is not narrowed (one bound covers listening and connecting), so the upstream set is enforced in code and tested.

7. HTTPS at the edge

The gateway terminates TLS 1.3 itself on a second port (tls_listen), with cancho’s TLS server written in cancho. Its certificates are read once, at start, from a directory that is compiled into the binary; the authority report names exactly that directory and /dev/urandom. No reload yet: a renewed certificate means a restart. ECDSA P-256 certificates only.

Deployment: deploy/examples/tls.toml

# Example 7: the gateway as the edge for one internal service.
listen = 8080
tls_listen = 8443
tls_dir = "/etc/cancho-gateway/tls"      # compiled into the binary: the program reads exactly this directory and /dev/urandom
tls_identities = ["api"]                 # /etc/cancho-gateway/tls/api/{chain.pem,key.pem,names}

[[upstream]]
name = "app"
addr = "127.0.0.1:9000"

[[route]]
name = "app"
path_prefix = "/"
upstream = "app"

1Make a certificate (any P-256 certificate works; this one is for localhost and lasts 30 days):

mkdir -p /tmp/gw-tls/api
openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt -out /tmp/gw-tls/api/key.pem
openssl req -new -x509 -key /tmp/gw-tls/api/key.pem -out /tmp/gw-tls/api/chain.pem -days 30 \
  -subj /CN=localhost -addext subjectAltName=DNS:localhost
echo localhost > /tmp/gw-tls/api/names

2Point a copy of the deployment at that directory (the file names /etc/cancho-gateway/tls) and run it, with the upstream of example 2 in terminal 1:

sed 's#/etc/cancho-gateway/tls#/tmp/gw-tls#' deploy/examples/tls.toml > /tmp/tls-demo.toml
scripts/try.sh /tmp/tls-demo.toml

3Ask over HTTPS. The upstream is told the client spoke TLS, and the access-log line says so:

curl --cacert /tmp/gw-tls/api/chain.pem https://localhost:8443/hello
upstream :9000 saw
GET /hello
Host: localhost:8443
Via: 1.1 cancho-gateway
X-Forwarded-Host: localhost:8443
X-Forwarded-Proto: https
X-Request-Id: 444d37-1f90-00000001
body bytes: 0

# terminal 2, the access log:
{"t":1791435851525,"id":"444d37-1f90-00000001","method":"GET","path":"/hello","route":"app","upstream":"app","status":200,"rule":"","outcome":"ok","ms":13,"upstream_ms":1,"bytes_in":0,"bytes_out":437,"tls":true}

4The plain port still works beside it, and says http; and the report names the two paths:

curl -s localhost:8080/hello | grep Proto
python3 scripts/authority.py --check
X-Forwarded-Proto: http
gateway-tls  args, clock, conn_accept, conn_read, conn_write, dir_read, file_read,
             fs_read("/dev/urandom"), fs_read("/etc/cancho-gateway/tls"), heap, io_write,
             net_in(""), net_out(""), poll

A client that handshakes and then sends nothing gets 408 at header_timeout_ms; one that never finishes its handshake is dropped without an answer at tls_handshake_ms, because there is no HTTP to answer with. Handshakes are bounded (tls_handshakes at a time, tls_rate a second, oldest first), and a handshake measured 12 ms of CPU on the development machine: set tls_rate from yours (docs/tls.md section 10).

8. EV chargers and a back office (OCPP over WebSocket)

Chargers keep a WebSocket open to the back office for days and speak OCPP-J on it (ocpp1.6 or ocpp2.0.1). The gateway checks the opening handshake and refuses what is wrong with a rule tag: a charger that offers a protocol the route does not serve, a browser page whose origin is not on the route’s list, a key that is not a key. It checks that the back office’s answer is a WebSocket answer to this request. After that the connection is a byte tunnel with an idle timeout and a lifetime. The gateway does not read the frames, so there is no message limit and no ping policy yet.

Deployment: deploy/examples/ocpp.toml

# Example 8: EV chargers (OCPP-J over WebSocket) connect to a back office through the gateway.
listen = 8080
ws_idle_timeout_ms = 600000      # a tunnel in which no byte moved for ten minutes is closed (two heartbeats at the usual 300 s)
ws_max_lifetime_ms = 86400000    # and none lives longer than a day: chargers reconnect
ws_max_tunnels = 64              # at most this many upgrades at once; the gateway's whole table holds 127 sessions

[[upstream]]
name = "csms"
addr = "127.0.0.1:9000"

[[route]]
name = "ocpp"
path_prefix = "/ocpp"
upstream = "csms"
websocket = true
subprotocols = ["ocpp1.6", "ocpp2.0.1"]   # a charger that offers neither is refused at the edge
# no `origins`: a browser (it always sends Origin) is refused here; a charger sends none and is admitted

[[route]]
name = "status"
path_prefix = "/"
upstream = "csms"

1Terminal 1, a small back office that answers BootNotification and Heartbeat (it is not an OCPP implementation); terminal 2, the gateway:

python3 scripts/demo_ws_upstream.py 9000        # terminal 1
scripts/try.sh deploy/examples/ocpp.toml        # terminal 2

2Terminal 3, a charger. It offers ocpp1.6, sends two calls and closes:

curl -si localhost:8080/ocpp/CP003 -H 'Upgrade: websocket' -H 'Connection: Upgrade' -H 'Origin: https://evil.example' \
  -H 'Sec-WebSocket-Version: 13' -H 'Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==' -H 'Sec-WebSocket-Protocol: ocpp1.6'
HTTP/1.1 400 Bad Request
...
{"type":"about:blank","title":"Bad Request","status":400,"rule":"ws.subprotocol","request_id":"211297-1f90-00000002"}

{"t":1791446975888,"id":"211297-1f90-00000001","method":"GET","path":"/ocpp/CP001","route":"ocpp","upstream":"csms","status":101,"rule":"","outcome":"ok","ms":3,"upstream_ms":1,"bytes_in":130,"bytes_out":368,"upgrade":"websocket"}
{"t":1791446975933,"id":"211297-1f90-00000002","method":"GET","path":"/ocpp/CP002","route":"ocpp","upstream":"csms","status":400,"rule":"ws.subprotocol","outcome":"refused","ms":0,"upstream_ms":0,"bytes_in":0,"bytes_out":261}
{"t":1791446975945,"id":"211297-1f90-00000003","method":"GET","path":"/ocpp/CP003","route":"ocpp","upstream":"csms","status":403,"rule":"ws.origin","outcome":"refused","ms":1,"upstream_ms":0,"bytes_in":0,"bytes_out":252}

A tunnel that nobody closes ends at ws_idle_timeout_ms or ws_max_lifetime_ms ("rule":"ws.idle-timeout" or "ws.lifetime" in its line, "outcome":"aborted"), and the gateway sends no WebSocket Close frame when it does: it does not parse frames, so it cannot know where one ends. Open tunnels are counted in the metrics (ws_tunnels_active). Add tls_listen (example 7) and the same route serves wss. At most 127 tunnels fit in the gateway’s slot table: ten thousand chargers need a different budget (docs/websocket.md section 9).

What these cases do not cover yet

  • Authentication and rate limiting: planned, not built. Do the check at your front for now.
  • TLS reload and a TLS-only deployment: not built (example 7 has a plain and a TLS port; a renewed certificate means a restart). WebSocket (example 8) is a byte tunnel: the handshake is checked, the frames are not read, so there is no message limit, no ping policy and no close handshake of the gateway’s own, and at most 127 tunnels fit.
  • The admin port (metrics, health) binds every interface and has no authentication: firewall it. No alerting, no tracing.
  • Client addresses in logs and headers: the compiler does not provide one yet.
  • Changing a route means a new binary; there is no hot reload.
