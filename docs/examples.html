Where it earns its place.

Six situations, each with the deployment file that makes it work and what the gateway answers and logs. Every refusal and field below is one the tests exercise; the list at the end is what it cannot do yet.

Download and try it

The configuration is compiled into the binary, so a release carries a demo gateway: it listens on port 8080 and forwards to one upstream on 127.0.0.1:9000. To point a gateway at your own upstreams you build your own, from the sources in the same release.

Download the binary (Linux x86-64) All assets and checksums 
chmod +x cancho-gateway-demo-linux-x86_64
python3 -m http.server 9000 &                  # any upstream will do
./cancho-gateway-demo-linux-x86_64               # one JSON line per request on stdout
curl -si localhost:8080/                         # Via and X-Request-Id added

Each release has the binary, cancho-gateway-demo.authority.json (what the compiler says the binary may do), cancho-gateway-src.tar.gz and SHA256SUMS; check with sha256sum -c SHA256SUMS. Built in CI at the pinned compiler by scripts/release.sh. It links only libc. If no release is listed yet, the first tag has not been pushed: build it from source. Alpha: not for production.

1. Internal APIs behind a TLS front

Caddy or nginx terminates TLS and sets X-Forwarded-For. The gateway sits behind it, believes that front, and gives every request an id the services and the audit log share.

listen = 8080

[[upstream]]
name = "orders"
addr = "10.0.1.5:9000"

[[route]]
name = "orders"
host = "api.example.com"
path_prefix = "/"
upstream = "orders"
trust_forwarded = true     # the party in front is mine: pass its headers on

With trust_forwarded = false (the default) a client’s own X-Forwarded-For, Forwarded and X-Real-IP are removed, so a caller cannot choose what the service believes about forwarding. A client’s X-Request-Id is kept only when it is 1 to 64 safe characters. The table.

2. One door for a few services

Route by host, then by the longest path prefix, and by method. Static files are read-only; a wrong method is refused at the door, not discovered at the service.

[[route]]
name = "web-static"
path_prefix = "/static"
methods = ["GET", "HEAD"]
upstream = "web"
max_body = 0

[[route]]
name = "web"
path_prefix = "/"
upstream = "web"
POST /static/app.js  -> 405  {"rule":"route.method", ...}
GET  /static/app.js  -> served by "web-static"
GET  /anything-else  -> served by "web" (the longest prefix that matches)
                        (with no "/" route at all: 404 {"rule":"route.none", ...})

Ties between two routes are a configuration error, found when the deployment is generated, not at 3 a.m.

3. Upload limits that are enforced

A route sets the largest body it accepts. The declared length is checked before a byte is forwarded; a chunked body is counted as it arrives.

[[route]]
name = "reports"
path_prefix = "/reports"
methods = ["POST"]
upstream = "reports"
max_body = 5242880          # 5 MiB
HTTP/1.1 413 Payload Too Large
{"status":413,"rule":"limit.body","request_id":"19b3c2a1f00-1f90-0000002c"}

The default is 1 MiB. A chunked body over the limit is cut off after part of it may already have gone upstream; the proxy notes say so.

4. A strict door in front of a lenient server

Old application servers and hand-written backends often disagree with a front proxy about where a request ends. That disagreement is request smuggling. The gateway refuses the ambiguous shapes and closes the connection, so the backend never sees them.

Content-Length and Transfer-Encoding together    -> 400 framing.two-lengths
two different Content-Length headers             -> 400 framing.length
obsolete header line folding                     -> 400 framing.fold
a bare LF as a line ending                       -> 400 framing.line-ending
CONNECT, or an absolute-form target              -> refused, own rule each

Tested against a corpus, split at every byte and mutated; the evidence page lists what that found.

5. A flaky upstream that should not take everything down

After a run of failures the gateway stops sending requests to that upstream for a while, answers at once, and lets one trial request through to see if it is back.

# in the deployment file
circuit_threshold = 5       # consecutive failures that open the circuit (0 turns it off)
circuit_open_ms   = 10000   # how long it stays open
connect_timeout_ms = 2000
upstream_timeout_ms = 15000
HTTP/1.1 503 Service Unavailable
{"status":503,"rule":"proxy.circuit-open","request_id":"..."}

Other upstream failures keep their own tags: proxy.connect, proxy.upstream-closed, proxy.head (all 502) and timeout.*. A dead idle connection is retried once, and only for a request with no body that is safe to repeat.

6. An audit trail and a capability report

When someone asks “what happened to request X” or “what can this process touch”, there is an answer for each.

{"t":1791376430841,"id":"594fe-1f90-00000001","method":"GET","path":"/orders/7",
 "route":"orders","upstream":"orders","status":200,"rule":"","outcome":"ok",
 "ms":12,"upstream_ms":11,"bytes_in":0,"bytes_out":1834}

{"id":"594fe-1f90-00000002","status":400,"rule":"framing.two-lengths",
 "outcome":"refused", ...}

The same id is in the response header and in a refusal’s body. The log goes to stdout, so journald, a file or a collector can take it; if that reader stops, so does the gateway (see the alpha notes).

gateway  args, clock, conn_accept, conn_read, conn_write, heap,
         io_write, net_in(""), net_out(""), poll        # no files, no foreign calls

That report is derived by the compiler and checked in CI: a build that gained a capability fails. The network bound is not narrowed (one bound covers listening and connecting), so the upstream set is enforced in code and tested.

What these cases do not cover yet

  • Authentication and rate limiting: planned, not built. Do the check at the TLS front for now.
  • TLS in the gateway itself, and WebSocket (for example OCPP between chargers and a back office): planned, not built.
  • Metrics and health endpoints: the access log exists; counters and an admin listener do not.
  • Client addresses in logs and headers: the compiler does not provide one yet.
  • Changing a route means a new binary; there is no hot reload.
